## Milestone 1 — Correctness (bugs found in review)

### 1.1 Pending → posted transactions lose every user edit, comment, and reaction

**Severity: data loss.** When Plaid posts a pending transaction it sends the
pending id in `removed` and a brand-new id in `added` with
`pending_transaction_id` pointing back. `TransactionSyncService.sync` deletes
the old row (cascading comments and reactions) and inserts a fresh one, so the
category, note, reviewed flag, visibility, splits, and the whole comment thread
vanish on every pending charge. For a Honeydue-style app this is the core loop
breaking.

- `Server/Sources/App/Plaid/PlaidModels.swift`: add `pendingTransactionId: String?`
  to `PlaidTransaction`.
- `Server/Sources/App/Services/TransactionSyncService.swift`: inside the write
  transaction, process `added` before `removed`. For each added tx with a
  `pendingTransactionId` that matches an existing row's `plaid_transaction_id`,
  **update that row in place** (new plaid id, amount, date, name, merchant,
  status → posted) keeping its UUID. Track the plaid ids you re-pointed and
  skip them in the `removed` loop.
- `Server/Sources/App/Database/TransactionStore.swift`: add
  `static func repointPending(from oldPlaidID:to tx:_ db:) -> Bool`.
- Test in `Server/Tests/AppTests/PlaidSyncTests.swift`: seed a pending tx via
  the mock transport, add a comment and a category, run a second sync page
  that removes the pending id and adds the posted one with
  `pending_transaction_id`, assert the UUID, category, and comment survive and
  status is `posted`.

### 1.2 Detection can permanently switch a series off

`RecurringStore.mergeDetected` writes `is_active = stored.isActive && detected.isActive`.
The intent was "user off stays off", but detection also produces `isActive =
false` whenever the last charge is older than two cadences (a skipped month, a
sync gap, a late initial sync). Once that happens the series can never turn
itself back on, so bills silently drop off the Upcoming list.

- Migration `v4_recurring_user_disabled`: `ALTER TABLE recurring_series ADD
  COLUMN user_disabled INTEGER NOT NULL DEFAULT 0`; backfill
  `user_disabled = 1 WHERE is_active = 0`.
- `RecurringStore.update`: `isActive` in the PATCH sets `user_disabled = NOT
  isActive` **and** `is_active`.
- `mergeDetected`: `is_active = detected.isActive && !stored.userDisabled`.
- Test in `BillsGoalsTests`: user toggles off → detection says active → stays
  off. Detection says inactive → later detection says active → comes back on.

### 1.3 Offline or flaky launch drops the user into "create a household"

`AppEnvironment.bootstrap` calls `/me`; on any non-401 failure
`session.household` stays nil, `needsHousehold` is true, and `RootView` shows
`HouseholdSetupView`. A user on a plane sees onboarding.

- `Budget/App/Session.swift`: persist the last `MeResponse` to
  `UserDefaults` (JSON) in `apply(_:)`; restore it in `init` when a token
  exists. Clear in `signOut`.
- `HouseholdStore.refresh`: on non-401 error keep the cached household and set
  `AppEnvironment.isOffline = true`; show a thin banner on `RootTabView`.
- Centralize 401: give `APIClient` an `onUnauthorized: () -> Void` set by
  `AppEnvironment` to `session.signOut()`, skipped for `v1/auth/apple`. Remove
  the per-store checks. Today only `refresh` signs out; every other 401 shows
  "Server error 401" forever.

### 1.4 Plaid dates land on the wrong day in US time zones

`TransactionSyncService.plaidDateFormatter` parses `YYYY-MM-DD` as **UTC
midnight**. The app groups by `Calendar.current.startOfDay`, so in any
American zone every transaction shows one day early, and a charge dated the
1st appears under the previous month in the app's day list. Server month
bucketing runs in the container's zone (UTC) so the *server* is consistent
with itself, but the dashboard's "this month" flips to the next month at 5 pm
Pacific on month end while the Budget tab still shows the old month.

- Parse Plaid dates at **12:00 UTC** (noon), so any zone within ±12 h shows
  the same calendar day. One line in the formatter setup plus a
  `.date(bySettingHour:)` shift. Add a `v4` data migration that rewrites
  existing `transactions.date` values ending in `T00:00:00Z` to `T12:00:00Z`.
- Routes stop deciding "current month" themselves: `GET /v1/reports/cashflow`
  gains `end=YYYY-MM` (default stays today for compatibility); the app always
  passes `month`/`end` from `Month(date: Date())` on the device. Same for
  `/v1/bills/upcoming` (`today=YYYY-MM-DD`), which currently uses the server's
  `startOfDay`.
- Test: a fixture tx dated `2026-08-01` maps into `Month(2026, 8)` under both a
  `America/Los_Angeles` and `UTC` calendar.

### 1.5 Dashboard budget card shows whatever month the Budget tab is on

`DashboardView.reload` calls `budgetStore.load()`, which uses
`budgetStore.month`. Step back two months on the Budget tab, return Home, pull
to refresh: the Home card now shows that month.

- Add `BudgetStore.loadCurrentMonth() -> MonthBudget?` that fetches
  `Month(date: Date())` into a separate `currentRollup` property; the dashboard
  reads that. `BudgetView` keeps `rollup`.

### 1.6 A category with negative rollover is treated as unbudgeted

`BudgetView.summarySection` and `DashboardView.budgetSection` filter on
`budgeted + rolloverIn > 0`. A $100 budget with −$150 rolled in (overspent
last month) has limit −$50, drops out of "Budgeted", and its spend is reported
as "spent outside any budget". `BudgetCategoryRow` shows "Set budget" for it.

- Filter on "a budget row exists for this month" (`store.budget(for:) != nil`)
  or `budgeted > 0 || rolloverIn != 0`. Row: when a budget exists and limit ≤
  0, show the bar full and red with "over by X".
- Move this "is budgeted" predicate into `BudgetProgress` in `BudgetModels`
  (`var hasBudget: Bool`) so both views and the server agree. Add
  `MonthBudget.budgetedEntries`.

### 1.7 Net-worth chart jumps at the final point when private accounts exist

Snapshots are household-wide (`allAccounts`), but `/v1/networth`'s `current`
is caller-visible. The app appends `current` to `series`, so a partner who
cannot see a private account gets a visible step at the end of every chart.

- Migration `v4_account_balance_snapshots`: `(id, account_id, date, current,
  available, UNIQUE(account_id, date))`. `NetWorthSnapshotCommand` writes one
  row per non-hidden account per day (keep writing the old household table
  for one release, then drop it in `v5`).
- `NetWorthStore.series(householdID:memberID:)` aggregates visible accounts
  only, via the same visibility predicate as `AccountStore.visibleAccounts`.
- This also unlocks per-account balance history (feature 4.8).

### 1.8 Sign-out never unregisters the push token after a relaunch

`PushRegistrar.lastRegistered` is in memory. Launch, sign out: the DELETE is
skipped and a shared device keeps receiving the previous user's reminders.
Persist the token in `UserDefaults` (`apnsToken`), read it in `unregister()`.

### 1.9 Members list is wrong until the next `/me`

`Session.apply(_ response: AuthResponse)` sets `members = [member]`. After a
fresh sign-in, Settings shows only you. Either include `members` in
`AuthResponse` (server + DTO) or call `householdStore.refresh()` right after
`signInWithApple` succeeds. Prefer the DTO change; it is one field.

### 1.10 Archived categories show as "Uncategorized" in the spending report

`ReportRoutes` builds names from `CategoryStore.list`, which excludes archived
rows. Add `CategoryStore.listIncludingArchived` and use it for the name map
(the picker keeps using `list`).

### 1.11 Search treats `%` and `_` as wildcards

`TransactionStore.list` interpolates the search text into `LIKE`. Escape `%`,
`_`, and `\` and add `ESCAPE '\'`. Test: searching `100%` matches only that.

### 1.12 Webhook sync failures are swallowed

`PlaidRoutes` webhook does `try? await req.transactionSync.sync(item:)`. A
broken Item fails silently forever. Log the error at `.error` with the item id.
(Item status handling is feature 3.1.)

### 1.13 Monthly `nextDate` drifts by 30-day steps

`RecurringDetector` sets `next = last + cadence.approximateDays` (30 for
monthly). A bill on the 31st predicts the 30th, then the 29th. Use
`BillProjector.nextOccurrence(after:cadence:calendar:)` (make it `public`) so
detection and projection step the same way. Test: last = Jan 31 → next = Feb
28/29, not Mar 2.

### 1.14 Transaction-detail section has an oversized gap (known TODO)

In the Simulator the "Category / Note / Reviewed" section shows extra vertical
space. Likely the `Menu` inside a `List` row expanding to the row's full
height, or the `TextField` with `.multilineTextAlignment(.trailing)` in an
`HStack`. Diagnose with the view debugger, fix, screenshot before and after.

### 1.15 Offset pagination skips or repeats rows when a sync lands mid-scroll

`cursor` is an integer offset. Replace with a keyset cursor encoding
`(date, created_at, id)` of the last row; the SQL becomes
`WHERE (t.date, t.created_at, t.id) < (?, ?, ?)`. Keep the field name
`nextCursor` (opaque string) so the app changes nothing.

**Milestone 1 exit:** all of the above merged, server tests ≥ 72, core tests ≥
26, Docker image builds, app runs in the Simulator through sign-in → sandbox
link → transactions → budget → bills with no visible regressions.

## Milestone 2 — Performance

Scale is a couple, so nothing here is urgent, but three of these are
quadratic and will be felt within a year of history.

### 2.1 Budget rollup is O(categories × months × transactions)

`BudgetCalculator.progress` calls `spent(...)` once per rollover level, and
each call scans every transaction. With 20 budgeted categories, 36 months of
rollover, and 6k transactions that is ~4M comparisons per `GET /v1/budgets`.

- In `monthBudget`, bucket once: `[String: Money]` keyed by
  `key(categoryID, Month(date:))`, built in a single pass that honors splits.
  Pass the bucket to `progress`/`rollover`. Memoize `rollover(into:)` per
  category in a dictionary during the walk.
- Keep the public signatures; add the bucketed path as the implementation.
  Add a test that asserts identical output to the current algorithm on a
  randomized fixture (keep the old function as `_referenceMonthBudget` in the
  test target only).

### 2.2 Every report loads the household's entire history

`TransactionStore.allVisible` is unbounded and is called by budgets, cashflow,
and spending. Add `from`/`to` to `allVisible`.
- Spending: the requested month only.
- Cashflow: the requested `months` window.
- Budgets: from the earliest month in the rollover chain. Compute it in SQL:
  `SELECT MIN(month) FROM budgets WHERE household_id = ? AND rollover_enabled = 1`,
  clamped to the requested month.

### 2.3 App renders blank, then populates, on every tab

Add a tiny `ResponseCache` (`Budget/Services/ResponseCache.swift`) that
stores the last decoded JSON per GET path in Application Support. Each store's
`load()` reads the cache first (synchronously, so the first frame has data),
then refreshes. Invalidate on sign-out and server-URL change. This is also the
foundation for widgets (5.2) and makes offline (1.3) genuinely useful.

### 2.4 Stores only refresh when empty

Every `.task { if store.x.isEmpty { await load() } }` means a tab opened once
never refreshes again unless pulled. Add `lastLoaded: Date?` to each store and
a shared `isStale(after: 5 min)`; refresh on `.task` when stale and on
`scenePhase == .active`.

### 2.5 Detection scans all history on every sync

`RecurringService.refresh` reads every shared transaction, then the detector
groups them. Bound the query to the last 24 months; yearly cadence needs at
least three points so 24 is the floor, not 12.

### 2.6 Missing index

`memberships(user_id)` is looked up on every authenticated request via
`requireMembership` and has no index. Add it in `v4`. Also
`transactions(household_id, category_id, date)` for the filtered list.

## Milestone 3 — Production readiness features

These are what stand between "works in sandbox" and "usable every day once
Plaid production is approved".

### 3.1 Item health and reconnect (ITEM_LOGIN_REQUIRED)

Today a bank that expires its consent fails every nightly sync with a log line
and nothing in the app. This is the most common Plaid production failure.

- Migration: `plaid_items` gains `status TEXT NOT NULL DEFAULT 'ok'`,
  `error_code TEXT`, `last_synced_at TEXT`, `last_error_at TEXT`.
- Webhook: handle `webhook_type == "ITEM"` codes `ERROR`
  (`ITEM_LOGIN_REQUIRED`), `PENDING_EXPIRATION`, `USER_PERMISSION_REVOKED`;
  set status. `TransactionSyncService`/`AccountSyncService` set
  `status = 'error'` + code on a Plaid API error and back to `ok` on success.
- `GET /v1/plaid/items` returns status; new `POST /v1/plaid/items/:id/update-link-token`
  creates a Link token in **update mode** (`access_token` in the body, no
  `products`).
- App: `LinkedInstitution` gains `status`; Accounts tab shows a "Needs
  attention" section with a Reconnect button that opens `PlaidLinkPresenter`
  with the update-mode token; Settings shows last-synced time per connection.
- Tests: webhook sets status; update-mode token request omits `products`.

### 3.2 Sync now

Transactions are only refreshed by webhook or the nightly cron. Add
`POST /v1/plaid/sync` (all of the caller's items), behind
`RateLimitMiddleware(limit: 6, window: 3600, name: "plaid-sync")` keyed per
user. Transactions pull-to-refresh calls it, then reloads. Show
`lastSyncedAt` in the Accounts net-worth card.

### 3.3 Session refresh

`SessionToken` is 60 days with no refresh; the comment in the file claims the
app silently re-auths, which it does not. Add `POST /v1/auth/refresh`
(authenticated, returns a new token). The app decodes `exp` from the JWT
payload (base64, no signature check) and refreshes when < 7 days remain, on
launch and on foreground.

### 3.4 Manual accounts and transactions

`AccountType.cash` exists but nothing can create it. Cash, a bank Plaid does
not support, or a loan to a friend all need this.
- Migration: `accounts.is_manual INTEGER NOT NULL DEFAULT 0`.
- `POST /v1/accounts` (manual only: name, type, visibility, starting balance),
  `POST /v1/transactions` and `DELETE /v1/transactions/:id` **only when the
  account is manual** (Plaid rows stay Plaid-owned), and `PATCH /v1/accounts/:id`
  accepts `currentBalance` for manual accounts.
- App: "Add manual account" in the `+` menu; "Add transaction" on a manual
  account; swipe-to-delete on manual rows only.
- Net worth already includes them via `allAccounts`.

## Milestone 4 — Daily-use features (server support exists; UI missing)

### 4.1 Transaction filters and a "needs review" inbox

The server already accepts `from`, `to`, `accountId`, `categoryId`. Add
`uncategorized=1` and `unreviewed=1` filters, a filter sheet on Transactions,
and a "N to review" row on the dashboard that opens the list pre-filtered.
This is the couple's weekly reconcile loop and it is currently one search box.

### 4.2 Category rules

"Always file `NETFLIX` under Entertainment." Table `category_rules(id,
household_id, merchant_key, category_id, created_at, UNIQUE(household_id,
merchant_key))` using `RecurringDetector.normalize` as the key. Applied in
`TransactionSyncService.map` before Plaid's category. When the user
recategorizes in the detail view, offer "Apply to all N from this merchant"
which creates the rule and bulk-updates matching uncategorized-or-auto rows.
Add `source TEXT` (`plaid`, `rule`, `user`) to `transactions` so a rule never
overrides a manual choice.

### 4.3 Split transactions UI

`splits` is fully supported server-side (`splitsBalance` validation, split-
aware rollups) and has zero UI. Add a "Split" screen from the detail view:
rows of category + amount, a live remainder line, save disabled until it
balances. Show a split badge in `TransactionRow`.

### 4.4 Category management

Create / rename / pick icon / archive / reorder via the existing routes. A
"Categories" screen under Settings. Reorder with `.onMove` writing
`sortOrder`. Un-archive needs `CategoryStore.list` to optionally include
archived rows (share with 1.10).

### 4.5 Bills: mark paid automatically

`BillStatus.paid` exists but is never produced. In `BillProjector`, accept an
optional `recentTransactions: [Transaction]` and mark an occurrence `.paid`
when a transaction whose normalized merchant matches the series' `merchantKey`
lands within −3…+5 days of the due date. Pure BudgetKit change with tests;
the route passes the visible transactions for the window. `RecurringSeries`
needs `merchantKey` on the DTO (already in the DB).

### 4.6 Goal contributions: edit and delete

Mistyped contributions can only be corrected by a negative entry. Add
`PATCH/DELETE /v1/goals/:id/contributions/:cid` recomputing `current_amount`
in the same transaction, and swipe actions on the ledger.

### 4.7 CSV export

`GET /v1/transactions/export.csv?from=&to=` (visible rows, RFC 4180, UTF-8
BOM for Excel). App: Share button on Transactions producing a `ShareLink`
with a `Transferable` file. Cheap and useful for taxes.

### 4.8 Account detail screen

## Milestone 5 — Delight

### 5.1 Partner activity feed and comment pushes

`GET /v1/activity?since=` returning comments and reactions by the *other*
member, newest first; a bell on the dashboard with an unread count persisted
in `UserDefaults`. Push a notification through the existing `PushService`
when a partner comments on a transaction you own (thread by transaction id).

### 5.2 Widgets

Lock Screen and Home widgets: "budget left this month" and "next bill". Read
from the `ResponseCache` (2.3) via an App Group container. The Hemera project
in this workspace has the App Group + widget timeline pattern to copy.

### 5.3 Category colors

`colorHex` exists on categories and is never rendered. Use it for the budget
bars and the spending chart, with a palette picker in 4.4.

## Verification checklist (per item)

1. Unit tests for the change (server or BudgetKit), and the full suites green.
2. Docker build green when the server changed.
3. Simulator walkthrough of the touched screen with a screenshot saved to the
   scratch dir; for server-only changes, a curl transcript.
4. `docs/code-map.md` updated if a file was added or moved; `docs/architecture.md`
   if a locked decision changed (none are expected to).
5. Commit message: imperative subject, a body that states the bug or feature
   in one sentence and the non-obvious decision in another. End with the
   Co-Authored-By trailer. Do not push unless asked.
